## 新结论：场景采用「AI底图 + 程序化动态层」

原计划把AI贴图整体列为不推荐，理由主要来自“16名角色 × 多姿态”的成本。
这个判断适用于角色，**不适用于场景**：场景只有3个，却铺满整个屏幕，是目前美术投入
回报最高的部分。

推荐结构：

```text
AI生成的静态环境底图（真正的地点、构图、材质、光影）
  + 现有Canvas远景动态（薄雾、热浪、水光、缓慢视差）
  + 现有Canvas前景粒子（符文、火星、灵泉微光）
  + 程序化暗角 / 色调统一 / 受击闪光
  + 角色与战斗UI
```

这样分工的原因：

- AI擅长一次性产出环境概念图，但不擅长稳定生成可循环动画。
- Canvas擅长低成本动态效果，但很难凭几何图形画出建筑、岩层、水体和空间纵深。
- 静态图片不会破坏“无构建步骤”。现有服务器已经支持 PNG/JPG，浏览器也能直接加载。
- 图片加载失败时保留当前渐变和程序化背景作为兜底，不会白屏。
- 后续新增场景时，只需再生成一张底图和一组颜色参数，不需要重做渲染系统。

## 美术方向：墨境不是普通仙侠背景

三个场景必须像出自同一个世界，而不是三张互不相关的AI壁纸。先锁一套共同语言：

- **媒介感**：东方水墨幻想，但不是纯黑白宣纸；使用墨洗边缘、矿物色、少量发光灵能。
- **形体语言**：大块留白与清晰剪影，远景层次明确，不堆碎细节。
- **材质**：湿墨、粗纸纤维、岩石裂纹、水面薄雾；避免塑料感和通用3D游戏截图感。
- **光线**：低调、侧逆光、局部辉光；角色必须能从背景里读出来。
- **构图**：宽幅战斗舞台，地平线稳定；不要人物、文字、UI、徽标、武器或单一巨大主体。
- **可玩性优先**：背景不是海报。中下部要能承载双方角色卡和特效，不能满屏高对比细节。

三个场景各自的身份：

| 场景 | 视觉命题 | 关键元素 | 必须避免 |
|---|---|---|---|
| **墨色虚空** | 世界尚未被书写完成 | 悬浮墨岩、断裂书页般的地层、远处淡银符痕、深紫黑虚空 | 普通星空、科幻太空站、满屏银河 |
| **赤焰熔岩** | 墨被高温烧成赤红裂纹 | 黑曜石台地、朱砂熔流、烟柱、灰烬、远处炉山 | 西式地狱、巨大恶魔、过曝橙红一片 |
| **碧蓝灵泉** | 灵能像墨在水中舒展 | 青碧泉面、层叠石台、雾中亭影或残碑、发光水脉 | 热带瀑布、写实旅游照、亮蓝塑料水 |

## AI作图怎么用

### 工具

本项目可以直接使用 Codex 内置图像生成能力，不需要先安装其他软件，也不需要用户提供
API Key。它适合生成场景概念图和最终底图。本轮只规划，用户确认后才实际生成。

外部工具不是必需品：

- **Photopea / Krita**：以后若需要手工裁切、局部压暗、修接缝，可选；第一轮不要求学习。
- **Photoshop / Figma / Canva**：对这类游戏环境底图没有必要，不作为主线依赖。
- **Stable Diffusion / ComfyUI**：只有未来需要大批量、固定seed或训练专属风格时才值得引入；
  三张背景没有必要先承担这套复杂度。

### 生成策略：不要一次生成三个场景

AI环境图最大的风险不是“画不出来”，而是三张风格不一致。正确顺序是：

1. 只选一个场景做**风格试片**，同一需求生成3个方向明显不同的候选。
2. 用户选一张最接近游戏气质的，不满意就只改一个变量继续迭代。
3. 把选中的图作为风格参考，再生成另外两个场景。
4. 最终三张统一做色调、对比度和构图检查。

首个试片推荐 **碧蓝灵泉**：它同时包含水墨、东方建筑/残碑、水面、雾和灵能光，
最能检验这套风格到底是“墨境”还是普通AI仙侠图。熔岩太容易靠红色显得唬人，
虚空又太容易变成抽象壁纸，都不适合承担第一次风格判断。

### 首轮提示词骨架（实际生成前还会按界面截图微调）

```text
Use case: stylized-concept
Asset type: 2D turn-based battle game environment background
Primary request: 碧蓝灵泉，一处由墨与灵能形成的东方幻想战场
Scene/backdrop: 青碧泉面、层叠深色石台、雾中残碑与极淡亭影，水脉发出克制的青蓝微光
Style/medium: painterly East Asian ink-wash fantasy environment concept art; visible paper and wet-ink texture;
              restrained mineral pigments; not photorealistic, not generic anime
Composition/framing: wide 16:9 establishing shot; stable low horizon; broad readable battle stage;
                     no single central hero object; low-detail lower and side regions for game units and UI
Lighting/mood: quiet, mysterious, cool side light, soft volumetric mist, restrained glow
Color palette: deep ink navy, mineral teal, muted cyan, tiny pale-gold accents
Constraints: environment only; no people, creatures, text, symbols that resemble writing, logos, watermark or UI;
             no frame or border; avoid busy high-contrast foreground detail
```

## 分阶段执行

### Scene 0 — 先做风格试片，不接游戏

- [x] 截一张当前战斗界面作为构图参考，测试时保持静音并在结束后关标签页。
- [x] 用“碧蓝灵泉”提示词生成3张候选，只用于对比，不进入仓库。
- [x] 用户按四项选择：世界观吻合、角色可读性、构图、是否有明显AI味。
- [ ] 若都不满意，只针对一个变量改第二轮，不同时改风格、构图和配色。
- [x] 选定 A 的矿物水墨 + B 的图形剪影作为风格母版，使用 Codex 内置图像生成。

**停损点**：两轮仍没有一张达到“愿意放进游戏”的水平，就停止AI底图路线，回到程序化
多层场景，不继续批量生成。

### Scene 1 — 单场景技术试装

- [x] 将选中的灵泉图复制进 `assets/scenes/`，使用稳定英文文件名。
- [x] 场景数据增加 `art` 配方；无图片时继续使用现有渐变兜底。
- [x] 底图使用 cover 裁切，保留Canvas粒子层；不引入构建工具或第三方运行库。
- [x] 场景选择卡直接预览同一张底图，确保“选择时看到的”和“进去后看到的”一致。
- [ ] 检查常见16:9分辨率，尤其1366×768与1920×1080；不能把重要轮廓裁掉。
- [ ] 检查角色、血条、技能特效和文字可读性；必要时由代码叠加局部压暗，不回炉重画。

**验收门槛**：用户明确认为它比现有程序化灵泉更好，而且没有牺牲战斗信息可读性。
没过门槛就删掉试装字段，现有背景完整恢复。

### Scene 2 — 补齐三个场景

- [x] 以灵泉母版为世界媒介参考，分别生成墨色虚空、赤焰熔岩。
- [ ] 每个场景最多两轮、每轮最多3张候选，避免无止境抽卡。
- [x] 三张统一检查笔触、色彩浓度、地平线位置与细节密度。
- [x] 各场景保留独有动态层：虚空符尘、熔岩火星/热浪、灵泉水光/薄雾。
- [x] 图片转为 WebP；三张合计约 410KB，单张均低于 1MB。
- [x] 在 `docs/SCENE_WORKFLOW.md` 记录生成模板、选图逻辑与新增场景流程。

### Scene 3 — 程序化层精修（只做AI底图缺的东西）

- [ ] 轻微远近视差：底图极慢位移，粒子层速度更快；幅度要小，避免晕动。
- [ ] 景深粒子：远小暗慢、近大亮快。
- [ ] 暗角和场景统一调色，但不能压黑角色与血条。
- [ ] 大伤害时只做短促亮度/色温反馈，不让整张底图剧烈抖动。
- [ ] 页面失焦、切场景和离开战斗时正确停止动画，避免后台持续耗电。

## 图片规格与接入原则

- 初稿按宽幅生成；最终资源优先约 **2048×1152（16:9）**。
- 环境图禁止内嵌文字，避免AI文字错误和本地化问题。
- 原始候选不全部进仓库，只保存最终采用图和最终提示词。
- 底图文件不是依赖；项目仍然零 npm 运行时依赖、零构建步骤。
- 图片必须有渐变兜底。加载慢时先看到对应场景颜色，而不是白屏或黑屏。
- 不为背景增加阻塞式“资源加载完成才能开战”；背景晚到时自然淡入即可。
- 不把AI生成图直接当作碰撞、规则或关卡数据，图片永远只是表现层。

## 角色与音乐的后续位置

### 角色：继续暂缓

角色只有约100×92像素的战场画布，做16套逐帧贴图投入巨大、细节又看不见。
先观察新场景是否让现有程序化角色显得不协调，再决定：

1. 保留程序化角色并调轮廓/明暗；
2. 只做16张选人界面立绘，战斗小人仍程序化；
3. 用现有骨架做AI参考，生成分层部件贴到骨架上。

不会直接跳到“16人 × 多姿态逐帧动画”。

角色小人的细化路线、16 人视觉身份证、AI 概念试片边界与分阶段验收，见
[`CHARACTER_ART_PLAN.md`](CHARACTER_ART_PLAN.md)。当前只完成方案，未生成角色资源，
也未修改或提交工作区中的 `stickman.js` 原型。

### 音乐：场景之后单独立项

原计划的五声音阶、加权随机游走和战况自适应方向可以保留，但不与场景首轮混做。
先把视觉风格确定，音乐才知道应该偏空灵水墨、厚重鼓点还是更抽象的灵能音色。

## 决策摘要

- **先做场景是对的。** 它只有3份资源，却覆盖最大屏幕面积。
- **主线用AI作图，但只负责静态底图。** 动态氛围继续由代码负责。
- **先试一张灵泉、三选一，再谈其余两个。** 不一次批量做完。
- **任何阶段都能回退到现有程序化背景。** 不满意就停，不让沉没成本绑架后续选择。
- **本轮不执行。** 下一步只有在用户确认后，才进行 Scene 0 的三张风格试片。
