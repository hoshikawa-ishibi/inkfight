# RECORDS_PLAN · 战绩记录与分享

打完一局，数字看一眼就没了。这份计划要做的是：**把每一局留下来，
并且让它能带出这台电脑，同时不能被随手改成 9999 伤害。**

## 要解决的三件事

| # | 问题 | 做法 |
|---|---|---|
| 1 | 打完就丢，没有历史 | 每局结算时自动写入本机战绩，战绩室可查 |
| 2 | 想给朋友看，没有办法 | 一串分享码（复制 / 存文件），朋友粘进游戏就能看 |
| 3 | 朋友可以随手编数据 | 签名 + **自洽审计**双层校验，见下 |

## 防伪：两层，各挡一类人

这是纯前端游戏，没有服务器。**任何签名密钥都在玩家自己的浏览器里**，
所以做不到「绝对防伪」。能做到的是把两种不同的伪造成本抬起来，
并且**在界面上如实告诉玩家这道校验的边界在哪**——
写一个假的「已认证 ✓」比不做校验更糟。

**第一层 · HMAC-SHA256 签名**
挡「拿记事本打开分享码，把 230 改成 9999」。改任何一个字节，签名立刻不符。
这是绝大多数人唯一会尝试的路径。

**第二层 · 自洽审计（`auditRecord`）**
挡「读了源码、拿到密钥、能重新签名」的人。签名可以重算，
但**一局战斗的数字之间有真实约束**，要伪造得整套编圆：

- 各单位伤害之和 = 该方总伤害（治疗、击杀同理）
- 最高单次伤害不能超过打出它那个单位的总伤害
- 最高单次伤害的名字必须是场上真实存在的单位
- 角色 id 必须在花名册里，每方人数必须等于该模式的编制
- MVP **不进分享码**，由 `mvpOf()` 从各单位数据现算——伪造不了「MVP 是谁」这一项
- 回合数、时间戳、数值范围的合理性

两层都过才显示「✔ 已验证」；签名过但审计不过，显示「⚠ 数据不自洽」并说明哪一条对不上。

## 落地位置（沿用现有分界线）

`core` / `data` 能在 Node 里 import，`game` / `view` 不能。签名和校验是纯逻辑，
必须落在 `core`，才能被 `npm test` 覆盖到。

| 文件 | 新增内容 |
|---|---|
| `src/core/sha256.js` | 纯 JS SHA-256 + HMAC-SHA256。**浏览器和 Node 共用同一份**——`crypto.subtle` 是异步的且依赖安全上下文，`node:crypto` 浏览器里没有，两边各用一套就是本项目最常出 bug 的形状 |
| `src/core/record.js` | 记录的数据模型：`makeRecord` / `mvpOf` / `summarize` / `auditRecord` |
| `src/core/share-code.js` | 分享码编解码 + 签名：`encodeShare` / `decodeShare` |
| `src/game/save.js` | 三个新 key：本机战绩、好友档案、本机昵称 |
| `src/view/records.js` | 战绩室 UI（本机战绩 / 生涯统计 / 好友榜 / 导入导出） |
| `src/game/battle.js` | `showResult` 里调一次 `commitRecord()` |
| `test/record.test.js` | SHA-256 标准向量、签名往返、篡改检出、审计规则、生涯统计 |

`mvpOf` 现在写在 `battle.js` 的 `renderStatsPanel` 里，这次搬进 `core/record.js`，
结算面板改成调它——**同一份知识两份实现是本项目的头号病因**，不再新增一份。

## 补录

用户 2026-09-02 的截图里那一局（困难 · 赤焰熔岩 · 4v4 · 胜）会作为一条
`backfilled: true` 的记录种进本机战绩，界面上带一个「补录」小标。

## 验收

- `npm test` 全绿（新增测试含 SHA-256 标准向量）
- 浏览器里打一局，结算面板出现「已记入战绩」，战绩室能看到

## 收尾（2026-09-02，全部完成）

做出来的东西和计划一致，另外补了三样计划里没写的：

- **自己的分享码导回来会并进「我的战绩」，不是变成好友。**
  换浏览器、清过缓存之后靠这条路能把战绩接回来——本来只是个边界情况，
  结果它是这个功能唯一的备份手段。
- **签名在解析之前验。** 原来的顺序是先 `JSON.parse` 再验签，
  于是被改坏的分享码往往先在解析上炸掉，玩家收到的是一句「格式不对」，
  掩盖了真正的原因。现在改坏内容会明确报「签名对不上」。
- **「我打出过的单场最高伤害」只算我方单位。** 原来遍历全部单位，
  观战局里 AI 打的 382 会被算成「我的」最佳——这一行会说谎。

### 实测（浏览器，2026-09-02）

| 项 | 结果 |
|---|---|
| 单局 4v4 分享码长度 | 336 字符（贴进聊天框刚好） |
| 整册 2 局 | 576 字符 |
| 改动分享码任意一个字符 | 一律拒绝，报「签名对不上」 |
| 改数字后**重新签名**（模拟读过源码的人） | 签名有效 ✔ / 数据不自洽 ✖，并指出「1 方的伤害分项之和 10252 对不上总计 483」，不入库 |
| 人机对局记录 | mode=ai / diff=hard / side=1，审计通过 |
| 观战对局记录 | side=null，计入总场次但不计胜率 |
| 弹窗三条关闭路径（按钮 / 点背景 / ESC） | 都走 `dismiss()`，无残留遮罩 |

### 一个绕过去的坑

内置浏览器把隐藏标签页的 `setTimeout` 钳到 1 秒，一整局要跑好几分钟。
实测时临时把 `setTimeout` 换成 MessageChannel 驱动的虚拟时钟
（**保留相对先后顺序**，只是不等真实时间），一局 4 秒跑完。
以后要在这个环境里做长流程 UI 实测，用这一招，别硬等。
